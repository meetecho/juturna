Nodes
=====

Juturna's basic node is the fundamental abstraction upon which Juturna's data
processing pipelines can be built. It embodies a simple design philosophy:
complex data flows can be made robust, testable, and composable by treating
each processing unit as an independent, message-driven actor with well-defined
boundaries.

A simple message processor
--------------------------

At its essence, a node is a typed message transformer: it receives messages of
type ``T_Input``, performs a designed task, and optionally emits messages of
type ``T_Output``. This generic type signature is not just decorative, but
rather it enforces a contract that makes pipeline composition predictable and
type-safe. Whether a node generates data from scratch, enriches incoming
records, or writes results to disk, it always conforms to this same conceptual
shape.

.. admonition:: Multi-input nodes and clashing types
    :class: :NOTE:

    Whilst node input type finds an easy match for single-input nodes, there
    might be cases where a node receives messages of heterogeneous types (think
    of a node that needs to mix audio and video data). Such a node receives
    the messages of its inputs one at a time, and tells them apart by their
    creator: see `Multiple inputs`_.

In Juturna, a node can play three distinct roles, all sharing the same
underlying implementation:

- **source nodes** originate data, pulling from APIs, databases, live streams,
  or generating synthetic content;
- **processor nodes** (often called ``proc`` in the codebase) sit in the middle
  of pipelines, transforming messages and making them available for intermediate
  steps;
- **sink nodes** terminate data flows, persisting results or delivering them to
  external systems.

This tripartite division reflects a classic pattern in stream processing, but
Juturna unifies them under one class because the differences are primarily about
how a node obtains its input, not how it processes it. A source node simply has
its input generated by a dedicated thread rather than received from upstream
nodes.

It is also worth mentioning that the taxonomy of node roles is purely
conceptual: nothing in a node class or in its configuration says which role it
plays. A node is a source if it sets a source function, and a sink if it
transmits nothing.

In a pipeline configuration, a node is its name, the class that implements it,
and the arguments for that class:

.. code-block:: json

  {
    "name": "my_awesome_node",
    "type": "contrib.acme.nodes.MyAwesomeNode",
    "configuration": { }
  }

Threading model
---------------

Every node runs up to two independent threads, each with a singular
responsibility. This separation of concerns is the key to the framework's
responsiveness and fault isolation.

.. image:: ../_static/img/node.svg
   :alt: node
   :width: 100%
   :align: center

The ``_worker`` thread is the node's processing engine. It runs in every node,
and blocks on the node's inbound queue, waiting for incoming messages from
upstream nodes. When a message arrives, the worker records it in the telemetry
and calls the node's ``update()`` method with it. This is the only place where
user-defined processing logic should run, ensuring that the framework maintains
full control over threading, error boundaries, and lifecycle management.

.. admonition:: The inbound queue
   :class: :NOTE:

   Nodes use FIFO (First-In, First-Out) queues. This ensures messages are
   processed in the order they are produced, even when a source node generates
   data faster than its descendants can consume it. While ``update()`` is busy,
   new messages wait in the inbound queue; once the queue is full, upstream
   nodes block on it until there is room again.

For source nodes, the ``_source`` thread runs in parallel to the ``_worker``
thread. Its sole purpose is to repeatedly invoke a user-provided callable
(``_source_f``) and inject the resulting messages into the node's own queue.
The *pre* and *post* sleep modes allow fine-tuning of polling behavior, such as
waiting before generating data (useful for rate-limiting) or after (useful for
ensuring minimum intervals between calls).

In short:

#. A message is pushed in the node's inbound queue - a source node will write
   the message itself through the ``_source`` thread, while intermediate nodes
   will receive messages from other upstream nodes;
#. the ``_worker`` thread pops the received message from the queue, and invokes
   the blocking ``update()`` method with it, where the actual data elaboration
   and subsequent transmission downstream take place.

Multiple inputs
---------------

A node with several upstream nodes receives their messages one at a time, in
the order they reach its inbound queue. ``message.creator`` tells which node
sent each of them. When a node needs messages from more upstream nodes before
producing an output (matching keys across streams, aggregating windows of data,
enforcing timeouts), it keeps the pending ones in its state, available in
``update()`` as ``kwargs['state']``, and removes them once they are used:

.. code-block:: python

   def update(self, message: Message, **kwargs):
       pending = kwargs['state'].setdefault('pending', {'audio': [], 'video': []})
       pending[message.creator].append(message)

       if not (pending['audio'] and pending['video']):
           return

       audio = pending['audio'].pop(0)
       video = pending['video'].pop(0)

       ...

The state is kept by the pipeline for the whole life of the node, across
``stop()`` and ``start()``, and ``kill()`` does not clear it. A node is
responsible for discarding the messages it no longer needs, so that its state
does not grow forever.

.. admonition:: Synchronisers
   :class: :NOTE:

   Earlier versions put a buffer and a synchroniser between the inbound queue
   and ``update()``. The buffer, the ``next_batch()`` method and the ``sync``
   node configuration key were removed: implement the same policies in
   ``update()``, using the node state.

Only messages travel
--------------------

A node accepts ``Message`` objects only. Anything else is refused, wherever it
comes from: returned by the source function, passed to ``put()`` or to
``transmit()``, or found in the inbound queue. A refused item is logged as an
error and counted in the ``health`` of the node under ``rejected_items``; it
never reaches ``update()``, and the node goes on with the next message. A
source function with nothing to deliver returns ``None``, which is not counted.

``transmit()`` offers the message to every destination. When a destination
fails, the others still receive it, then the first error is raised.

Node lifecycle
--------------

A node's life follows a clear progression managed by the pipeline:

.. code-block::

   configure() → warmup() → start() → stop() → destroy()

The ``status`` property, backed by the ``ComponentStatus`` enum, makes this
state machine explicit.

``configure()`` and ``warmup()`` prepare the node: the first is called right
after the node is built, the second once all the nodes of the pipeline exist
and are linked. Use ``configure()`` for what depends on the outside world
(ports, connections), and ``warmup()`` for the internal state (loading a
model).

``stop()`` stops the source thread first, then lets the worker thread finish
the messages left in the queue. ``kill()``, used by the pipeline when it is
killed, discards them instead.

When things go wrong
--------------------

An exception raised by ``update()`` or by the source function does not stop
the node: it is logged, counted in the ``health`` of the node, and the node
moves on to the next message. A source function that keeps failing is called
less and less often, up to ``JUTURNA_SOURCE_MAX_BACKOFF`` seconds apart, until
it works again.
